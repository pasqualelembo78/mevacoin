===========================================================================
# FIX 1: `inSk.mask` — FATTORE DI BLINDING SBAGLIATO (30 Giu 2026)
===========================================================================

## Causa

`rct::zeroCommit(amount)` restituisce `1*G + amount*H` — il fattore di blinding è 1
(lo scalare `rct::identity()` = `{0x01, 0x00, 0x00, ...}`).

Ma il wallet impostava `src.mask = rct::zero()` = **0** per output non-RCT.

Questa incongruenza di 18 righe, ereditata da Monero, non si era mai vista perché
Monero ha migrato tutti gli output non-RCT a RingCT prima dell'attivazione di CLSAG.

## La Matematica

Output non-RCT con ring_size=1:
```
pubs[l].mask = zeroCommit(amount) = 1*G + amount*H   ← blinding factor = 1
inSk.mask   = 0                                        ← blinding factor = 0
C_offset    = a*G + amount*H                            ← pseudoOut
z           = inSk.mask - a_pseudo = 0 - a = -a

C_precomp   = pubs[l].mask - C_offset
            = (1*G + amount*H) - (a*G + amount*H)
            = (1-a)*G                                    ← DL = 1-a

Ma z*G = (-a)*G (DL = -a). I logaritmi discreti differiscono di 1:
C_precomp ha DL = 1-a
z*G       ha DL = -a

Quindi C_precomp ≠ z*G, e la formula L diventa:
L = s*G + c_p*P + c_c*C_precomp
  = aG + c*mu_C*((1-a) - (-a))*G
  = aG + c*mu_C*G               ← TERMINE EXTRA c*mu_C*G
```

Il termine extra `c*mu_C*G` corrompe la hash chain → `final_c ≠ c1` → CLSAG fallisce.

## Il Fix

File: `src/wallet/wallet2.cpp:10070`
```diff
- src.mask = td.is_rct() ? td.m_mask : rct::zero();
+ src.mask = td.is_rct() ? td.m_mask : rct::identity();  // scalare 1, coincide con zeroCommit
```

Con `src.mask = 1`:
```
z = inSk.mask - a_pseudo = 1 - a
C_precomp = (1-a)*G = z*G   ✓
L = aG - c*mu_P*p*G - c*mu_C*(1-a)*G + c*mu_P*p*G + c*mu_C*(1-a)*G = aG   ✓
```

Questo fix corregge anche il percorso MLSAG in `proveRctMGSimple`.

## Verifica (ring_size=1)

Dopo il fix, la transazione team-lock (ring_size=1, niente decoy) passa:
```
CLSAGDBG[1]: final_c=91c8f2b4...  c1=91c8f2b4...  diff=0
```

**MA** ring_size=2 falliva ancora! → è emerso il secondo bug.

# FIX 2: ORDINE ANELLO DIVERSO TRA SIGNER E VERIFIER (1 Lug 2026)
===========================================================================

## Causa

Per output unmixable (anello più piccolo del minimo richiesto), il wallet **non ordinava**
i membri dell'anello per indice globale. Lo `std::sort` era dentro un blocco `else`:
```cpp
if (outs.back().size() < fake_outputs_count + 1) {
    // gestione unmixable — NON ordina
} else {
    std::sort(...);  // ← ordina solo se l'anello è pieno
}
```

La conversione da indici assoluti a relativi (`cryptonote_format_utils.cpp:1510`) **ordina
sempre** in modo crescente:
```cpp
std::sort(res.begin(), res.end());  // "giusto per sicurezza"
```

Quindi:
- **Signer (wallet)**: usa l'anello NON ordinato: P[0]=indice_1, P[1]=indice_0
- **Verifier (daemon)**: ricostruisce l'anello dagli offset (ordinati): P[0]=indice_0, P[1]=indice_1

Stessi elementi, ma in ordine diverso → `mu_P = H("CLSAG_agg_0" || P_0 || P_1 || ...)`
produce hash diversi → tutta la catena del CLSAG diverge → `final_c ≠ c1`.

## Il Fix

File: `src/wallet/wallet2.cpp:9709-9728`
Lo `std::sort` viene eseguito **sempre**, indipendentemente dalla dimensione dell'anello.

## Verifica (ring_size=2)

Network fund transfer (400k MVC, extra 0xC0 per network fund):
```
Signer:  mu_P = eeee4a49...
Verifier: mu_P = eeee4a49...   ← IDENTICI!
final_c == c1, diff = 0
```
Tx `2a30a040b012d93895407cb12ecd45ef866a374a1e4bc63993b389a142f2b8f9` accettata nel mempool.

# TRAPPOLE e LEZIONI IMPARATE
===========================================================================

## 1. `zeroCommit` è una mina per output non-RCT
Restituisce `1*G + amount*H`, non `0*G + amount*H`. Lo scalare 1 implicito deve
essere RIPRODOTTO OVUNQUE.

## 2. `rct::identity()` ≠ `rct::zero()` (confermato dai sorgenti)
```cpp
// identity(): scalare 1
static const key I = {{0x01, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00,
                        0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00,
                        0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00,
                        0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00}};
// zero():     scalare 0
static const key Z = {{0x00, ...}};
```

## 3. Un fix nel sorgente NON significa un fix in esecuzione
Il wallet-rpc DEVE essere riavviato dopo la ricompilazione. Controllare con `ps aux`.
Il demone NON serve ricompilarlo (il fix è solo nel wallet, lato produzione firma).

## 4. Transazioni fallite avvelenano il mempool
Una tx rifiutata resta nel mempool del daemon. Il wallet vede la key_image e marca
l'UTXO come `spent=true`. Soluzione: `flush_txpool` + rescan wallet.

## 5. Il logging MDEBUG (--log-level 4) è stato essenziale
Confrontare ogni valore intermedio tra wallet e daemon ha permesso di individuare
esattamente la discrepanza (L vs aG, e poi l'ordine di P[0]/P[1]).

# PROBLEMA: "double spend" / "0 unlocked" DOPO TRANSAZIONE PRECEDENTE
===========================================================================

## Sintomo
Dopo una transazione finita nel mempool (anche se rifiutata o non minata),
la prossima volta che apri il wallet:
```
  Balance: 0.0000 unlocked / 399998.9985 total MVC (0 UTXO(s))
✗ ERROR: Insufficient unlocked balance
```

## Causa
Il wallet registra nella cache locale:
1. La **key_image** dell'UTXO originale — l'output risulta `spent=true`
2. Il **change output** della transazione — ma è `locked` perché non minato in un blocco

Né l'uno né l'altro sono spendibili → `unlocked_balance = 0`.

Anche se si svuota il mempool del daemon (`flush_txpool`), la cache del wallet
rimane sporca — il wallet non sa che la transazione è stata rimossa.

## Soluzione (fixata in auto.py)

`refresh_wallet()` adesso fa **sempre** flush del pool + rescan:

```python
def refresh_wallet():
    flush_stale_pool_tx()          # 1. svuota pool
    wallet_rpc("rescan_blockchain") # 2. ricostruisce cache da zero
    flush_stale_pool_tx()          # 3. ri-svuota (nel caso sia arrivata altra roba)
```

Così il wallet riparte sempre da uno stato pulito: UTXO originale = unspent, 0 locked.
