# THE BLOCKER: CLSAG VERIFICATION FAILURE
===========================================================================

**SYMPTOM**: ALL transactions fail with "invalid input" at daemon.
Daemon log: `verRctCLSAGSimple failed for input 0` inside `verRctNonSemanticsSimple`.

**AFFECTS**: ALL wallets and ALL ring sizes identically:
- Founder (regular keys, ring_size=1,2,11)
- Network fund (deterministic keys, ring_size=1,2,11)
- Treasury (deterministic, ring_size=1,2,11)

**NOT wallet-specific**: same error regardless of key type → points to systematic issue
in transaction construction or CLSAG implementation.

## Daemon Verification Flow (what passes, what fails)

| Step | Result |
|------|--------|
| `check_ring_size()` — unmixable exception | PASS |
| `check_tx_input()` → `scan_outputkeys_for_indexes()` — DB pubkey lookup | PASS |

| `verRctSemanticsSimple()` — range proofs + balance | PASS |

| **`verRctCLSAGSimple()` — actual CLSAG crypto** | **FAIL** |

## What I've Verified (all ruled out)

### 1. Secret key correctness
Founder uses regular spend key extracted from wallet. Network fund uses deterministic key
from "mevacoin_network_fund". Both fail identically → NOT a key derivation issue.

### 2. Ring pubkeys match
Wallet gets pubkeys via `get_outs.bin` RPC. Daemon looks up same outputs via
`scan_outputkeys_for_indexes`. Both query the same DB → keys must match.
Additionally, `rv.mixRing == mix_ring` check in `expand_tx_and_ver_rct_non_sem` passes
(no "mismatched pubkeys/mixRing" error).

### 3. Commitment for non-RCT outputs
- Wallet: `rct::zeroCommit(amount)` = `amount * H`
- Daemon (db_lmdb.cpp:4258): `data.commitment = rct::zeroCommit(amount)`
Both produce same commitment. Verified at code level.

### 4. outPk.dest mismatch
During signing (rctSigs.cpp:1157): `rv.outPk[i].dest = copy(destinations[i])` − set from vout key.
During deserialization (expand_transaction_1): `rv.outPk[n].dest = rct::pk2rct(output_public_key)`
− set from same vout key. Match confirmed.

### 5. get_pre_mlsag_hash mismatch
Both signing and verification call `get_pre_mlsag_hash(rv, hwdev)` with same `rv` state.
The hash includes: `rv.message` + serialized `rctSigBase` (mixRing, outPk, ecdhInfo, pseudoOuts)
+ bulletproof data. All fields are populated identically on both sides.

### 6. zero_governance_sigs_in_extra corruption
Only modifies extra when 0xB0/0xB1/0xB2 governance tags found. Founder wallet has no such tags
(extra contains only tx_pub_key). Function returns `false` without modification.

### 7. Build mismatch
Both mevacoind and wallet-rpc built from same source at same time (78cb3eb04).

### 8. CLSAG ring_size=1 unsupported
CLSAG spec supports n≥1. Performance test `sig_clsag.h` works with various ring sizes.

## CLSAG Math Verification (manual trace)

For non-RCT output with ring_size=1:
- `inSk = (derived_secret_key, mask=0)`
- `a` = random pseudoOut mask
- `Cout = a*G + amount*H` (pseudoOut)
- `C[l] = pubs[l].mask - Cout = amount*H - (a*G + amount*H) = -a*G`
- `z = inSk.mask - a = 0 - a = -a`
- `P[l] = output_pubkey = derived_secret_key * G`

The CLSAG proves: P[l] = p*G AND C[l] = z*G = (-a)*G

During verification with ring_size=1:
- Start with c = sig.c1
- Compute L = s[0]*G + c*mu_P*P[0] + c*mu_C*C[0]
  = (a - c*(mu_P*p + mu_C*(-a)))*G + c*mu_P*(p*G) + c*mu_C*(-a*G)
  = a*G - c*mu_P*p*G + c*mu_C*a*G + c*mu_P*p*G - c*mu_C*a*G
  = a*G ✓ (reconstructs the initial aG from signing)
- Compute R similarly → a*H ✓
- c_new = H(aG, aH) should equal sig.c1

**Math checks out. The failure must be in data values, not the algorithm.**

# ROOT CAUSE: NOT FOUND (hypotheses in order of likelihood)
===========================================================================

## Hypothesis A: tx_prefix_hash mismatch ← MOST LIKELY
The `get_transaction_prefix_hash()` serializes `transaction_prefix` (version, unlock_time,
vin, vout, extra) and hashes it.

**Wallet side** (cryptonote_tx_utils.cpp:594-595):
```cpp
get_transaction_prefix_hash(tx, tx_prefix_hash, hwdev);
```
Called AFTER:
- Vin amounts zeroed ONLY for RCT sources (line 588-589)
  ```cpp
  if (sources[i].rct)
      boost::get<txin_to_key>(tx.vin[i]).amount = 0;
  ```
  For non-RCT sources (premine): `amount` is NOT zeroed — stays as real amount (200000000000000)
- Vout amounts zeroed (line 592)
  ```cpp
  for (size_t i = 0; i < tx.vout.size(); ++i)
      tx.vout[i].amount = 0;
  ```

**Daemon side** (tx_verification_utils.cpp:108):
```cpp
const crypto::hash tx_prefix_hash = get_transaction_prefix_hash(tx);
```
Called from deserialized blob. The blob was serialized by the wallet AFTER the above zeroing.
So the daemon sees the same serialized data → hash should match.

**HOWEVER**: The wallet uses `get_transaction_prefix_hash(tx, h, hwdev)` (hw::device version)
which delegates to `hwdev.get_transaction_prefix_hash(tx, h)`.
The default device calls `cryptonote::get_transaction_prefix_hash(tx, h)` (basic version).
The daemon calls `get_transaction_prefix_hash(tx)` (basic version directly).

Both serialize `transaction_prefix` with binary_archive and hash with cn_fast_hash.
Should produce identical results. **But this is the #1 suspect** because the amount zeroing
logic for non-RCT sources is unusual and could hide a bug.

### What to check for Hypothesis A
Add logging to BOTH sides showing the hex of the serialized prefix before hashing.
Compare wallet-side vs daemon-side prefix_hex.

## Hypothesis B: Non-RCT amount in vin breaks output lookup
At HF≥4, Monero convention is ALL version 2 txs have `txin_to_key.amount = 0`.
But the wallet doesn't zero it for non-RCT sources. Daemon's `scan_outputkeys_for_indexes`
uses `tx_in_to_key.amount` to look up outputs. For non-RCT sources, amount is real (non-zero).
Daemon finds output by amount → works, BUT the `absolute_offsets` computation might differ.

**Note**: This is unlikely because the output IS found (check_tx_input passes).

## Hypothesis C: Different `get_pre_mlsag_hash` between signing and verification
Both sides call `get_pre_mlsag_hash(rv, hwdev)`. But between signing and verification:
1. Transaction is serialized to blob and deserialized
2. `expand_transaction_1` runs on deserialization, which might modify `rv.outPk.dest`
3. `expand_transaction_2` overwrites `rv.message` and `rv.mixRing`

If the rctSigBase serialization differs between the two calls (because of `outPk.dest` or
other fields being set differently), the hash would differ.

**However**: signing code at line 1157 DOES set `rv.outPk[i].dest = copy(destinations[i])`,
and expand_transaction_1 sets it from the same vout pubkey. So `outPk.dest` should match.

## Hypothesis D: PseudoOuts size mismatch
For non-RCT sources, the pseudoOut commitment must be `a*G + amount*H`. If the wallet
uses wrong amount (e.g., 0 instead of real amount), the pseudoOut would be wrong.
But the wallet's `inamounts` should contain the real amounts.

## Hypothesis E: CLSAG implementation bug in this fork
The CLSAG code was forked from Monero. If any modifications were made during the fork
(mevacoin-specific changes), they could introduce bugs. Need to diff against upstream.
